# Проектирование устойчивой спутниковой группировки

Интерфейс для проектирования низкоорбитальной группировки и оценки её
устойчивости. Инженер собирает конфигурацию, сервис считает сутки работы
сети посекундной сеткой и показывает, где именно и почему пропадает связь.
Конфигурации сохраняются вариантами и сравниваются между собой.

Базовый набор кейса: 48 аппаратов в трёх плоскостях на высоте 550 км,
наклонение 87°, сутки расчёта шагом 120 с — 720 отсчётов.

---

## 1. Запуск

### В контейнерах

```bash
docker compose -f deploy/docker-compose.yml up --build
```

Интерфейс на <http://localhost:8080>. Порты меняются через `deploy/.env`
(скопировать из `deploy/.env.example`).

nginx фронтенда проксирует `/api/` на бэкенд и резолвит его адрес в
рантайме, поэтому стартует, даже пока бэкенд поднимается. Сценарии кейса
монтируются в контейнер томом из `case/Данные`.

### Локально, для разработки

Нужны [uv](https://docs.astral.sh/uv/) и Node 22+ (в образе — 24).

```bash
# терминал 1 — бэкенд
uv sync
cd backend && uv run uvicorn src.main:app --port 8000 --reload

# терминал 2 — фронтенд
cd frontend && npm ci && npm run dev
```

Интерфейс на <http://localhost:5173>, запросы `/api` проксируются на
`127.0.0.1:8000`.

### Если бэкенд не поднялся

Интерфейс не умрёт: при недоступном сервере он считает модель в браузере
(`lib/localSimulator.ts` — порт эталонной геометрии на TypeScript) и честно
показывает плашку **«локальный расчёт»**. Это запасной путь для демонстрации,
а не режим по умолчанию: **если плашка видна, числа считает браузер, а не
сервер.** Принудительно отключить сеть можно сборкой с `VITE_API_MODE=local`.

## 2. Пользовательский сценарий

**1. Загрузить проект.** Выбрать сценарий из набора кейса — список приходит
с сервера вместе с метаданными (очередь запуска, дальность ISL, число
отказов), поэтому варианты различимы до загрузки. Либо загрузить свой JSON
формата `cosmo-A-1.0`; файл проверяется, и при ошибках выводится весь их
список с путями до полей, а не первая попавшаяся.

**2. Посмотреть, как это работает.** В центре — глобус с аппаратами, лучами
до наземных пунктов и текущим маршрутом. Внизу таймлайн: воспроизведение,
шаг вперёд-назад, скорость от ×1 до ×600. Позиции аппаратов интерполируются
в браузере, поэтому анимация плавная и не дёргает сервер.

**3. Прочитать показатели.** Правая панель, вкладка **«Показатели»** — по
каждому наземному пункту процент доступности, видимость, дельта к прошлому
расчёту и суточная полоса связи с осью часов. Наведение показывает причину
перерыва («перерыв 16:36–16:38, 2 мин, нет спутника»), клик по участку
переводит таймлайн на этот момент.

**4. Изменить конфигурацию.** Левая панель: этап развёртывания, фазирование
и параметры плоскостей, дальность ISL, порог возвышения, наземные пункты,
периоды недоступности аппаратов и шлюзов, стратегия маршрутизации.

Правка **не пересчитывает модель молча** — она копится в черновике, а сверху
появляется полоса со списком изменений и кнопкой «Пересчитать». Так каждый
расчёт осознанный, и его результат есть с чем сравнить.

**5. Сохранить вариант.** «Сохранить как вариант» кладёт конфигурацию вместе
с её расчётом на вкладку **«Варианты»**. За вариантом закрепляется цвет, он
переименовывается, и его конфигурацию можно вернуть в работу.

**6. Сравнить.** Отметить два и более варианта, выбрать базу — и открыть
сравнение (кнопка или клавиша `C`). Видно сводную таблицу с подсветкой
лучшего в столбце, полосы доступности на одной суточной сетке, максимальные
перерывы и дифф конфигураций: чем именно варианты отличаются.

**7. Выгрузить.** Результат выгружается в формате кейса
`cosmo-A-result-1.0` — `effective_scenario` ровно в том виде, в котором
считали, и маршруты по каждой паре «отсчёт × клиент». Выгруженный файл
загружается обратно без потерь.

Горячие клавиши: `[` и `]` сворачивают боковые панели, `C` открывает
сравнение.

## 3. Как считаются маршруты

Расчёт независим по отсчётам: сеть пересобирается на каждом шаге с нуля.
Для суток это 720 итераций четырёх шагов ниже.

### 3.1. Положение аппаратов

Круговые орбиты, аргумент широты растёт линейно:

```
r = R + altitude_km                  n = sqrt(MU / r³)
u = slot_deg + phase_deg + n·t       Ω = raan_deg
```

Константы: `R = 6371.0` км, `MU = 398600.435507` км³/с², период вращения
Земли `86164.09054` с. Земля доворачивается на `earth_angle0_deg + ω·t`.

Те же константы сервер отдаёт фронту в блоке `constants`, чтобы анимация
считалась теми же числами и не расходилась с расчётом.

### 3.2. Какие аппараты активны

Аппарат активен, если `launch_batch ≤ launch_stage` **и** момент не попадает
ни в один интервал `failures` для этого аппарата. Интервалы полуоткрытые:
`[start_s; end_s)`.

### 3.3. Рёбра сети

**Межспутниковые (ISL).** Между двумя активными аппаратами, если расстояние
меньше `isl_range_km` **и** линия связи не задевает Землю. Второе проверяется
честно: ищется ближайшая к центру Земли точка отрезка, и её радиус должен
быть больше `R`. При 3000 км эта проверка не срабатывает никогда, но начинает
работать при дальности выше ≈5408 км.

**Наземные.** Между наземным пунктом и активным аппаратом, если угол
возвышения не ниже `min_elevation_deg`. Шлюз, попавший в интервал
`gateway_outages`, рёбер не получает вовсе.

Считается векторизованно через numpy: попарные расстояния и углы возвышения
берутся одним проходом, а не циклом.

### 3.4. Поиск маршрута

Маршрут идёт от клиента до **любого** шлюза. Ключевое ограничение:
**наземные пункты трафик не ретранслируют.** Промежуточными узлами могут быть
только аппараты, а шлюз — только конечным. Без этого правила клиент мог бы
«дотянуться» до шлюза через другого клиента, и доступность оказалась бы
завышенной.

Две стратегии, переключаются в панели параметров:

| Стратегия | Алгоритм | Что минимизирует |
|---|---|---|
| `min_hops` | поиск в ширину от клиента | число переходов |
| `min_distance` | Дейкстра от клиента | суммарную дальность в км |

Обе останавливаются на первом же извлечённом шлюзе и восстанавливают путь по
массиву предков. Переключатель нужен, чтобы обосновать выбор: на полной
группировке `min_distance` даёт маршруты короче на 300–370 км при том же
числе переходов и той же доступности — то есть выигрыш в задержке достаётся
бесплатно.

### 3.5. Метрики и причины перерывов

Если маршрута нет, причина классифицируется от частного к общему:

| Код | Когда |
|---|---|
| `no_sat` | над клиентом нет ни одного видимого активного аппарата |
| `gw_down` | все шлюзы выключены по `gateway_outages` |
| `no_gw` | ни один шлюз не видит ни одного аппарата |
| `isl_break` | спутниковая сеть разорвана между клиентом и шлюзом |

Соседние отсчёты без маршрута склеиваются в перерывы; перерыв, упирающийся в
начало или конец суток, помечается `at_boundary` — его длительность занижена
границей расчёта, и учитывать её наравне с остальными нельзя.

По каждому клиенту считается: `availability_pct` (доля отсчётов со сквозным
маршрутом), `visibility_pct` (доля отсчётов, где виден хоть один аппарат),
`target_met`, `max_gap_s`, `total_outage_s`, список перерывов, статистика
переходов с гистограммой и средняя длина маршрута в километрах. По сценарию
в целом — достигнут ли порог всеми, худший пункт и средняя плотность сети.

### 3.6. Стоимость

Сутки, 720 отсчётов, 48 аппаратов — **около 200 мс**, из них ~165 мс
геометрия и ~40 мс маршрутизация. Ответ 920 КБ, под gzip ~25 КБ.

Поэтому расчёт запрашивается **один раз целиком**, а таймлайн дальше
крутится локально: сервер во время воспроизведения не дёргается.

## 4. Что считает сервер, а что браузер

Граница проведена жёстко, и путать её не стоит.

**Сервер считает все числа**, которые попадают в показатели, сравнение и
выгрузку: рёбра сети, маршруты, причины перерывов, метрики, сводку.

**Браузер считает только картинку** — положение аппаратов между отсчётами,
чтобы анимация шла плавно, по тем же константам, что прислал сервер.

Сервер **не хранит состояние**: ни базы, ни сессий, ни идентификаторов
вариантов. Сценарий целиком приходит в теле каждого запроса. Это прямое
следствие требования выгружать `effective_scenario` — сервер обязан считать
ровно то, что ему прислали. Варианты проекта живут на фронте.

## 5. API

Контракт — `docs/openapi.yaml`, типы фронта в `frontend/src/types/api.ts`
повторяют его один в один.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/health` | живость и версия |
| `GET` | `/api/scenarios` | список встроенных сценариев с метаданными |
| `GET` | `/api/scenarios/{id}` | полный JSON сценария |
| `POST` | `/api/scenarios/upload` | загрузка файла, `multipart/form-data` |
| `POST` | `/api/validate` | валидация без расчёта |
| `POST` | `/api/simulate` | полный расчёт на весь горизонт |

Некорректный сценарий — **нормальный результат, а не сбой**: HTTP 200 и
`valid: false` со списком всех найденных ошибок, у каждой путь до поля, код
и человекочитаемое сообщение. Коды 4xx оставлены за ошибками протокола:
нечитаемое тело, неизвестная стратегия маршрутизации, файл больше 10 МБ.

## 6. Форматы данных

**Вход, `cosmo-A-1.0`** — задан кейсом: `environment` (орбита, сетка времени,
пороги), `design` (плоскости, аппараты, этап развёртывания), `ground_sites`
(клиенты и шлюзы; шлюзов может быть несколько), `failures`,
`gateway_outages`.

**Выход, `cosmo-A-result-1.0`** — `effective_scenario` со всеми правками
пользователя и `routes`: по записи на каждую пару «отсчёт × клиент», включая
те, где маршрута нет. Для базовых сценариев это 720 × 3 = 2160 записей.

## 7. Стек

**Бэкенд** — Python 3.13, FastAPI, [msgspec](https://jcristharif.com/msgspec/)
вместо pydantic (ответ на 920 КБ сериализуется заметно быстрее), numpy для
векторной геометрии, uvicorn. Ответы сжимаются gzip-middleware.

**Фронтенд** — React 19, TypeScript, Vite 8, [Mantine 9](https://mantine.dev)
для интерфейса, [CesiumJS](https://cesium.com/platform/cesiumjs/) для
глобуса, zustand для состояния.

Графики нарисованы инлайновым SVG без charting-библиотеки: размер бандла от
них не растёт, а вся нужная гибкость — подсветка лучшего, пунктир порога,
общая суточная сетка для всех вариантов — всё равно требовала бы ручной
вёрстки.

**Развёртывание** — Docker, nginx раздаёт статику и проксирует API.

## 9. Проверки

```bash
# бэкенд: сверка с четырьмя эталонными суточными расчётами
cd backend && uv run uvicorn src.main:app --port 8000   # в отдельном терминале
uv run python backend/tests/check_against_fixtures.py

# фронтенд
cd frontend
npm run typecheck      # tsc --noEmit
npm run check          # орбитальная механика против эталона на Python
npm run check:local    # локальный расчёт против фикстур
npm run check:export   # выгрузка и обратная загрузка
```

`check_against_fixtures.py` сверяет ответ `/simulate` с
`frontend/tests/fixtures/simulate-*.json` — четырьмя полными суточными
расчётами независимой реализации. Сравниваются рёбра сети на каждом шаге,
маршруты, причины перерывов, сами перерывы, метрики, гистограммы переходов,
константы и сводка. Расхождение показывается до конкретного клиента и
отсчёта, а не как «вроде похоже».

## 10. Ограничения

- Модель круговых орбит без возмущений: ни J2, ни атмосферного сноса. Для
  суточного горизонта это допустимо, на неделях уже нет.
- Пропускная способность и загрузка каналов не моделируются: ребро либо
  есть, либо нет.
- Тень Земли считается цилиндрической (`geometry.sunlight`) и в метрики не
  входит.
- Ручки `/snapshot` и `/export` описаны в openapi, но не реализованы:
  фронту они не нужны — позиции он считает сам, выгрузку строит на клиенте.
- Варианты проекта хранятся в `localStorage` браузера, а не на сервере.
