# Фронтенд — проектирование спутниковой группировки

React 19 + TypeScript + Vite + CesiumJS + Mantine + Zustand.

## Запуск

```bash
cd frontend
npm install          # если node_modules собирался на другой платформе — сначала rm -rf node_modules
npm run dev          # http://localhost:5173
```

По умолчанию фронтенд полностью автономен: исходные сценарии загружаются из
`public/mock/`, а геометрия, связи, маршруты и метрики считаются в браузере.
Запросов к отсутствующему API в этом режиме нет. Когда бэкенд будет готов,
режим переключается переменной `VITE_API_MODE=remote`.

```bash
npm run build        # сборка в dist/
npm run typecheck    # tsc --noEmit
npm run check        # сверка TS-порта физики с geometry.py
npm run check:local  # сверка полного локального расчёта с 4 фикстурами
npm run check:export # сверка выгрузки с форматом кейса cosmo-A-result-1.0
```

## Архитектура

```

  lib/localSimulator.ts полный расчёт сети для автономного mock-режима
  lib/cesiumScene.ts   ЕДИНСТВЕННОЕ место, где живёт Cesium (императивно)
  api/client.ts        HTTP-клиент по docs/openapi.yaml + режим фикстур
  stores/project.ts    сценарий, результат, варианты (Zustand)
  stores/playback.ts   время и проигрывание
  lib/compare.ts       модель сравнения вариантов: агрегаты, дифф, вердикт
  lib/strip.ts         сжатие 720 отсчётов в участки «связь / перерыв»
  lib/viz.ts           токены визуализации, палитры, форматирование, склонения
  types/api.ts         типы по OpenAPI
  theme.ts             тёмная тема Mantine
  components/          React-компоненты интерфейса (+ CSS-модули)
  components/charts/   полосы, дельты, легенда, плитки (инлайновая вёрстка)
```

### Почему Cesium отдельно от React

Cesium императивный: он владеет своим canvas, своим циклом отрисовки и
своими объектами. Оборачивать его в реактивность React (как делает resium) —
значит получить два источника истины и утечки при размонтировании.

Поэтому `cesiumScene.ts` — обычный класс. `GlobeView.tsx` создаёт его в
`useEffect` с пустыми зависимостями, дёргает `update()` из
`requestAnimationFrame` и уничтожает в функции очистки. React про Cesium не
знает ничего, а кадровый цикл читает сторы через `getState()` — подписки там
нет, иначе рендер дерева гнало бы на 60 fps.

### Время: 60 fps мимо React

`playback.ts` держит непрерывное модельное время в обычном мутируемом объекте
`playbackTime`, вне стора: его читает только сцена Cesium. В React время
публикуется примерно 12 раз в секунду — этого хватает часам и ползунку.
Дискретный `stepIndex` (сетка 120 с) считается из опубликованного времени.

### Производные значения лежат в сторе

`clients`, `gateways`, `nSteps`, `stepS`, `horizonS` пересчитываются в момент
смены сценария или результата и хранятся в состоянии, а не вычисляются
селектором. Селектор, возвращающий новый массив на каждый вызов, ломает
`useSyncExternalStore` React 19 («The result of getSnapshot should be cached»).

### Почему позиции считаются на фронте

Бэкенд отдаёт состояние сети на сетке 120 с — это дискретные отсчёты,
интерполировать их нельзя. Но спутник за 120 с пролетает 911 км, и если
рисовать только по отсчётам, картинка будет дёргаться.

Поэтому позиции считает `orbital.ts` по тем же формулам, что и `geometry.py`,
с непрерывным временем. Константы (`mean_motion_deg_s`, радиус орбиты)
приходят с сервера в блоке `constants`, чтобы расчёты не разъехались.

**Правило: фронт считает координаты только для картинки. Все числа в
таблицах, метриках и выгрузке приходят с бэкенда.**

Совпадение порта с эталоном проверяется автоматически:

```bash
npm run check
# проверено точек: 384
# максимальное расхождение: 1.286e-12 км
# OK: TS-порт совпадает с эталоном
```

### Сферическая модель против эллипсоида

Кейс считает Землю сферой R = 6371 км, Cesium рисует эллипсоид WGS84.
Расхождение до ~21 км у полюсов — 0.3 % радиуса, визуально незаметно.
Наземные пункты ставятся средствами Cesium (`fromDegrees`), спутники —
по координатам модели. На числа это не влияет, потому что числа не отсюда.

### Черновик и посчитанное

Правка конфигурации не запускает расчёт. «Описание данных» кейса говорит:
«Сервис загружает файл, отображает параметры и **рассчитывает** состояние
сети» — и следом: «**Изменение настроек в интерфейсе создаёт новый вариант
проекта**». Первое про загрузку, второе про правку: это разные события.

Поэтому в сторе два состояния:

- `scenario` — черновик, то, что крутит пользователь;
- `committed` — конфигурация, которой соответствует `result`.

Пока они расходятся, `stale = true`, а список правок копится в `pending`
(«RAAN P2: 60.0° → 75.0°»). Повторные правки одного поля схлопываются:
у ползунка важны исходное и конечное значения. Вернули значение обратно —
запись исчезает. Полоса `RecomputeBar` показывает список и даёт две кнопки:
пересчитать или откатить черновик.

Что рисуется из чего:

| Из черновика (верно сразу) | Из расчёта (ждёт пересчёта) |
|---|---|
| позиции спутников, кольца орбит | рёбра сети, маршрут |
| состав активных аппаратов | метрики, перерывы, причины |

Состав активных — чистая функция конфига (`launch_batch <= launch_stage`
и отсутствие отказа на момент `t`), ровно как его считает `geometry.py`,
поэтому `GlobeView` считает его сам и не ждёт сервер. Сеть — результат
расчёта: пока он устарел, линии рисуются почти прозрачными, маршрут не
подсвечивается, полоса доступности гаснет, таблица метрик приглушена и
помечена «устарело». Ничего не прячется — но и не выдаётся за актуальное.

Кнопка «Пересчитать» передаёт текущий черновик локальному симулятору. Поэтому
результат учитывает очередь запуска, RAAN, фазирование, дальность и порог связи,
а также периоды недоступности аппаратов и шлюзов — готовая фикстура расчёта
не подставляется.

### Что кейс разрешает менять

ФТ1 постановки требует редактировать очередь запуска, ориентацию плоскостей,
фазирование и периоды недоступности — это и есть обязательная часть.

Блок `environment` кейс задаёт как условия набора, но дальность ISL в нём
меняется от файла к файлу (3000 в сценарии 01, 2000 в 04), а постановка
допускает «дополнительные средства сценарного анализа». Поэтому дальность и
порог возвышения выведены в ползунки: вместо двух точек из разных файлов
можно пройти диапазон и увидеть, где рвётся сквозной маршрут. Исходные
значения файла хранятся в `envBaseline`, отклонение показывается в панели.

`horizon_s` и `step_s` намеренно оставлены только для чтения: постановка
требует сравнивать варианты на одном периоде расчёта. Высота и наклонение —
тоже, они задают саму задачу кейса.

### Варианты проекта

Сервер без состояния, поэтому сохранённые варианты живут в сторе и
`localStorage` (ключ `cosmo.variants.v1`). Вариант весит ~150 КБ —
заводить ради этого БД незачем, а требование «сохранить вариант и
вернуться к нему» закрывается полностью.

### Один источник проекта, один способ выбрать пункт

В шапке рядом стояли три безымянных контрола: список сценариев набора, кнопка
«Загрузить JSON» и выпадающий список наземного пункта. Связь между первыми
двумя была неочевидна (это одна вещь или две?), а третий дублировал карточки
пунктов в панели показателей — одно и то же состояние меняли из двух мест.

Теперь в шапке одна кнопка-меню «откуда взят проект»: набор кейса и свой файл
стали пунктами одного выбора, а в самой кнопке видно текущий ответ. Текущий
сценарий определяется по `scenario.meta.id`, а не отдельным состоянием выбора —
иначе после загрузки своего файла список показывал бы прошлый выбор.

Пока проект не загружен, меню в шапке не показывается: тот же выбор уже стоит
в центре стартового экрана двумя большими кнопками. Подзаголовок шапки убран
совсем — состав проекта читается в панели параметров, а название сценария
теперь в самой кнопке.

Наземный пункт выбирается там, где он показан: кликом по карточке в панели
показателей или кликом по самому пункту на глобусе. Второе стало возможным
после того, как обработчик клика сцены научился различать аппараты
(`PointPrimitiveCollection`, там id — строка) и наземные пункты (`Entity`,
строка лежит на объекте). Шлюз не выбирается: маршрут строится до него, а не
от него.

### Плоскости раскрываются, выделение плоское

Список плоскостей был плоским: на каждую по два ползунка с подписями. Растёт
линейно их числу, а формат количество не ограничивает — в наборе кейса три,
но жюри может принести файл с десятком. Теперь это раскрывающиеся строки:
свёрнутая показывает идентификатор и оба угла («P2 · RAAN 60.0° · фаза 7.5°»),
раскрыта одна за раз. Секция занимает ~180 px вместо ~600 px, а строки
разделены волосяными линиями, а не слипаются в простыню. Плоскость, чьи углы
разошлись с посчитанными, помечена точкой — та же правка перечислена в полосе
пересчёта.

Сегментные переключатели (этап развёртывания, стратегия маршрутизации,
«значения / дельты» в сравнении) лишились вертикальных линеек между пунктами:
плашка активного пункта наезжала на них, соседняя линейка уходила под неё, и
ряд выглядел рваным — третий сегмент казался не отделённым от второго.

Отдельно пришлось убрать протёкший селектор. В `ConfigPanel.module.css` стояло
правило `.panel label`, которое цепляло вообще все `label` внутри панели —
включая внутренние `label` Mantine. Сегментному переключателю доставался
`margin-top: 8px`, его лейбл уезжал вниз, а вместе с ним и плавающий индикатор
(он позиционируется по боксу лейбла): заливка активного пункта стояла не по
центру полосы, а высота контрола раздувалась с 30 до 42 px. Подписи полей
теперь по классу `.fieldLabel`.

Само выделение — **прямоугольная полупрозрачная заливка без скругления и без
рамки**, от края до края сегмента. Ориентир — активный пункт навигации в Zed
(`background: rgba(7, 74, 207, 0.25)`, `color: #85acfa`, `border-radius: 0`):
активный сегмент читается как часть полосы, а не как пилюля поверх неё. Тем же
приёмом выделена раскрытая плоскость. Оформление задано один раз
в `styles/main.css`, поэтому все переключатели приложения выглядят одинаково.

### Состав аппаратов зависит от момента времени

Подпись «Активно N из M» под выбором очереди раньше считала только выведенные
на орбиту, без учёта периодов недоступности. Из-за этого сценарий
«03 Отказ 10 аппаратов» показывал «Активно 48 из 48» и все аппараты белыми:
формально верно для `t = 0` (отказы в этом сценарии начинаются с шестого
часа, `start_s: 21600`), но выглядело так, будто отказы проигнорированы.

Теперь подпись показывает текущее число, отдельно «в отказе N» и «не
выведено N», а под ней — кликабельная подсказка «Ещё 10 аппаратов уходят в
отказ в 6.0 ч →», которая переводит шкалу времени к этому моменту. В списке
периодов каждая строка помечена состоянием: `СЕЙЧАС` (красная метка),
`с 6.0 ч`, `завершён`; клик по строке тоже переводит шкалу. Список
отсортирован по времени начала, но удаление работает по исходному индексу
в сценарии.

### Недоступность шлюза не редактируется

В проекте единственный шлюз выхода в наземную сеть, и его отключение — не
проектное решение, а авария: выбирать её в форме нечего. Кнопку «Выключить
шлюз на 0–6 ч» и редактирование `gateway_outages` из интерфейса убрали.

Само поле сценария поддерживается полностью: формат `cosmo-A-1.0` его
содержит, расчёт учитывает периоды, причина `gw_down` классифицируется и
попадает в разбор перерывов. Если загруженный файл задаёт такие периоды,
они показываются в панели параметров **только для чтения**, со статусом
(`СЕЙЧАС` / `с 6.0 ч` / `завершён`) и переходом по шкале времени. В четырёх
сценариях набора `gateway_outages` пуст, поэтому секции там просто нет.

### Периоды недоступности объединяются, правки схлопываются

«Пересекающиеся интервалы объединяются по смыслу недоступности» — прямая
цитата из описания данных. Раньше можно было задать аппарату S19 период
0–24 ч, а сверху ещё 12–24 ч, и в сценарий попадали оба: аппарат оказывался
«дважды недоступен». Теперь перекрывающиеся и соприкасающиеся периоды одного
аппарата сливаются в один, а период, целиком входящий в уже заданный,
отклоняется с сообщением.

Ключ записи в списке ожидающих правок — сам период (`fail:S19:0:86400`), а не
счётчик вызовов. Поэтому добавить отказ и тут же его снять — это ноль правок,
а не две записи. Раньше каждое действие получало уникальный ключ, и список
рос: «Отказ S19 0–24 ч», «Отказ S19 12–24 ч», «Снят отказ S19 0–24 ч» — три
записи там, где по факту не осталось ничего. Снятие периода помечено в чипе
пунктирной рамкой и зачёркиванием, чтобы не путалось с добавлением.

### Правая панель: карточки, аналитика — отдельным окном

Раньше правая панель шириной 24rem держала четыре разные задачи: вердикт,
разбор по пунктам, список вариантов и таблицу сравнения. Таблица
`варианты × пункты` в такую ширину не влезала физически — в CSS стояли
`white-space: nowrap` и обрезка подписей по `max-width: 9rem`; открытая
раскрывашка пункта выталкивала сравнение за пределы экрана.

Разделено по принципу «обзор в панели, разбор в модальном окне»:

- **Показатели** — три плитки вердикта и по карточке на наземный пункт:
  крупный процент, полоса доступности с осью
  часов, риской текущего отсчёта и подсказкой при наведении
  («перерыв 16:36–16:38, 2 мин, нет спутника»). Клик по участку переводит
  шкалу времени. Подробности — разбор по причинам и список перерывов —
  раскрываются внутри карточки.
- **Маршрут** — без изменений: текущий маршрут по участкам и карточка аппарата.
- **Варианты** — карточки сохранённых конфигураций: чекбокс «в сравнение»,
  выбор базы, переименование, возврат конфигурации, отличия от базы и выгрузка
  каждого эксперимента в обязательном формате `cosmo-A-result-1.0`.
  Кнопка «Добавить вариант из файла» принимает и сценарий кейса, и выгруженный
  результат: файл разворачивается до сценария, считается и сразу сохраняется
  вариантом, отмеченным для сравнения. Путь «сравнить с чужим сценарием» —
  два действия, без захода на другие вкладки.
- **Сравнение вариантов** — компактное модальное окно с тремя обязательными
  показателями по каждому пункту и таблицей изменённых параметров.

Логика сравнения вынесена в `lib/compare.ts` чистыми функциями: на входе
сохранённые варианты, на выходе структура для отрисовки. React там нет, стор
не читается — сравнение проверяемо отдельно от интерфейса.

### Цвета графиков считаны, а не подобраны

Палитры прогнаны через валидатор цветовых схем (полоса светлоты, минимум
насыщенности, различимость при дальтонизме, контраст к фону панели `#0b1220`):

| Шкала | Значения | Худшая пара |
|---|---|---|
| Серии вариантов, 6 слотов | `#3987e5 #d95926 #199e70 #c98500 #d55181 #9085e9` | CVD ΔE 8.4, нормальное зрение 19.3 |
| Состояние канала | связь `#2a6fb0`, перерыв `#d03b3b` | CVD ΔE 17.9, нормальное зрение 29.0 |

Прежняя пара «зелёный / красный» (`#22c55e` / `#ef4444`) давала ΔE **4.1**
при дейтеранопии: самый частый тип дальтонизма (~6 % мужчин) не отличал
связь от перерыва. Поэтому «связь» теперь синяя — различие держится на
светлоте, а не на оттенке, а красный остаётся тревожным цветом.

Цвет серии закреплён за порядковым номером варианта (`Variant.seq`), а не за
его позицией в списке: удаление соседа не перекрашивает остальные.

Ось доступности не обрезается — шкала всегда от нуля. Разница в доли процента
читается по числу у полосы и по вкладке дельт, а не за счёт растянутого
масштаба. Переходы, километры и число аппаратов показаны без отметки
«лучший»: короткий маршрут при 12 % доступности — не достоинство, а следствие
того, что длинных маршрутов не нашлось.

- Линии связи: ISL голубые, наземные жёлтые, текущий маршрут зелёный и толстый
- Наземные пункты: клиенты жёлтые, шлюзы красные, с подписями
- Кольца орбит (переключаются)
- Таймлайн: перемотка, play/pause, скорости ×1…×600, шаг по отсчётам
- Полоса доступности под таймлайном: синее — связь есть, красное — перерыв
- Клик по наземному пункту на глобусе выбирает его текущим
- Клик по спутнику → панель: плоскость, очередь, соседи, из каких пунктов виден,
  в чьих маршрутах участвует
- Разбор маршрута по участкам: uplink / ISL / downlink, дальности, задержка света
- Редактирование RAAN и фазирования плоскостей ползунками с пересчётом
- Пустой стартовый экран: пока сценарий не выбран, считать нечего
- Переключение очереди запуска
- Дальность ISL и порог возвышения ползунками, с отметками значений набора
  (3000 / 2000 км, 10°) и пометкой «изменено с …» при отклонении от файла
- Добавление и удаление периодов недоступности аппаратов
- Загрузка своего JSON с показом ошибок валидации по полям
- Черновик конфигурации: правки копятся списком, расчёт запускается кнопкой,
  есть откат. Сравнение живёт только в окне сравнения: дельту «стало / было»
  из панели показателей убрали — там не было видно, с чем идёт сравнение
- Карточки наземных пунктов: полоса доступности с осью, ховером и переходом по
  клику, разбор перерывов по причинам, список перерывов
- Сохранение вариантов: выбор участников сравнения и базы, переименование,
  чипы отличий от базы, возврат конфигурации
- Окно сравнения на всю ширину: вердикт, сводная таблица, полосы всех вариантов
  на одной сетке суток, разбор перерывов по причинам и длительностям,
  гистограмма переходов, дифф параметров, выгрузка CSV / JSON
- Локальный пересчёт сети и двух стратегий маршрутизации без backend
- Выгрузка варианта в `cosmo-A-result-1.0` и его повторная загрузка — как из
  меню в шапке, так и кнопкой на вкладке «Варианты» — с восстановлением
  стратегии маршрутизации и метки эксперимента
- Метка варианта закрепляется в `meta.title` / `meta.id` выгрузки
  («Полная группировка — Вариант 2», `01_full_constellation__v2`): исходный
  `meta.title` приходит из набора кейса и от правок параметров не меняется,
  поэтому без этого любой скачанный эксперимент возвращался под именем базового
  сценария. Кейс допускает собственные названия и идентификаторы при сохранении
  структуры данных
